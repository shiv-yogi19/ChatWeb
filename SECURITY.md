# SENDORA security notes (no independent audit; not formally verified)
**Auth:** on connect the Worker sends a fresh 128-bit nonce plus an ephemeral ECDH P-256 public key (single use, 15 s expiry). The client returns HMAC-SHA256 keyed by ECDH(client private key, server ephemeral key) over the nonce; the server verifies with its ephemeral private key (held in the socket attachment). Failure closes the socket (4003). Identity = first 128 bits of SHA-256(public key), computed by server and client. A newer authenticated session for the same identity replaces the older (4000).
**Messages:** ECDH P-256 -> HKDF-SHA256 (info binds both fingerprints) -> AES-256-GCM, random 96-bit nonce, AAD = sender|recipient|message id. Receivers drop repeated message ids per session.
**Verification:** users type the safety number read from the other device; "Verified" is set only on an exact match and is stored against the peer's fingerprint. A changed key is a different identity, so it shows as unverified.
**Server sees:** public keys, display names, online status, who messages whom, timing, ciphertext size. **Never sees:** plaintext, private keys.
**Server-side authorization:** acks and reactions are accepted only for message ids the server routed between those two identities (in-memory, cleared on DO restart/at 5000 entries).
**Limits:** private key is a JWK in localStorage (XSS would expose it); no forward secrecy (static ECDH); no account recovery; no IP-based auth-failure throttling; blocks are local only; origin check is not authentication.
**v0.2:** image/location payloads use the same AES-GCM path (each chunk has its own message id in the AAD). Browser history is plaintext in IndexedDB. Origin must be present and match. No forward secrecy, no independent audit. Browser-side code (history, images, notifications, location UI) has had syntax checks only, no automated or manual browser test.
